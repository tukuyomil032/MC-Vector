# Tile Queue, Storage, and Updates

## Scheduling model

Dynmap's `MapManager` coordinates worker threads, full-world render state,
pending tiles, update/touch work, and retries. MC-Vector uses the same behavior
as a design target while keeping ownership in Rust.

Priority order:

1. Tiles intersecting the visible viewport.
2. Adjacent tiles needed for a smooth pan.
3. Tiles around the latest player positions.
4. Explicit user refresh requests.
5. Background full-world work.

The queue is bounded and coalesces identical tile keys. A newer request for the
same key supersedes an older request unless the older request is already being
written atomically.

## Tile identity

```text
serverId
worldId
minecraftVersion
assetIdentity
rendererVersion
perspective
zoom
tileX
tileY
```

Changing any identity component invalidates the old tile namespace. A tile
generated by the current top-down prototype must not be returned as an
`IsoHDPerspective` tile.

## Disk storage

```text
map-cache/
  <server-id>/
    <world-id>/
      <minecraft-version>/
        <asset-hash>/
          <renderer-version>/
            <perspective>/
              <zoom>/<tile-x>/<tile-y>.png
```

Writes go to a temporary file in the same directory, flush successfully, and
then use atomic rename. A partial PNG is never a valid cache entry.

## Invalidation

`chunk_dirty` is a hint. Rust checks region modification time and read results
before regenerating. Only tile keys whose world-space rectangle intersects the
changed chunk are invalidated. A player update changes the marker layer and
does not invalidate terrain.

If a replacement render fails, the last successful tile remains visible with
`stale` metadata. If no successful tile exists, the UI reports `error`,
`empty`, or `asset_missing` explicitly.
