# ADR-MAP-0005: Exact Minecraft release support

**Status:** Accepted as an execution constraint. **Decision date:** 2026-09-23.

## Decision

The target is every exact Minecraft Java release in the maintained 1.14–26.3 snapshot, currently 48 entries. Each exact release owns five **release-verification stages**: assets, Anvil, Paper snapshot, Java reference/pixel parity and real acceptance. These are per-release evidence records, not five promises to write version-specific adapters. The reference/pixel stage requires the per-release Dynmap oracle and source-delta report defined in ADR-MAP-0017; listing an exact version or using the fixed baseline alone is not evidence of support. No family representative or neighboring patch substitutes for an exact release.

Version support means inspecting and comparing the exact release's renderer inputs, not creating one generic page or one duplicated Rust renderer per patch. The asset audit must enumerate direct ZIP entries in the exact client JAR and mappings/bytes in its exact asset index as separate source roots, then resolve them into a provenance-preserving canonical logical-resource map. Block registry IDs and complete state-property/value sets must be compared alongside blockstate selectors, selected model graphs, textures, tint/material/light data and resource source locations. A runtime-proven precedence rule is required for conflicting bytes at one logical path.

The ledger separates three claims. (1) An exact artifact/content fingerprint identifies the bytes and normalized renderer input for a release; equal fingerprints are required to claim there is no renderer-input delta. (2) A compatibility-profile ID identifies Rust behavior/format handling and may be shared across releases with different block, state, model, or texture data when the existing generic resolver is proven to process each changed input. (3) A version-specific adapter is required only when an observed format, API, or rendering-semantic change cannot be handled by an existing profile. Every changed renderer input still needs a stable change ID linked to exact-release fixtures, Dynmap traces, and passing Rust pixel comparisons. Parity report schema v2 records `implementationProfile.decision` as `baseline`, `shared_existing_profile`, or `new_adapter`, names the immediately previous release/profile, and lists exact per-change coverage. Fingerprint equality is never used as a substitute for per-change parity; a data-only change is not silently ignored merely because no Rust code change was needed. A `new_adapter` decision additionally requires the pre-adapter Rust failure, its fixture/reference trace, the implementing phase, and the adapter commit digest.

## Consequences

Official manifest membership is refreshed in the version-lock phase. Client/server/asset-index/Paper artifacts are identified by exact URL, version, declared size and cryptographic digest. The two-container probe in `../version-asset-container-audit.md` establishes the source inventory rule only; it is not a release delta or support proof. Unavailable official, compatible Dynmap oracle or Paper artifacts remain blocked and cannot be silently excluded from the target. New releases in range expand the exact-release evidence set. Additional implementation phases are created only for observed behavior gaps, not automatically for every release.
