## System Overview

MC-Vector is a cross-platform desktop application built with **Tauri v2** (Rust backend) and **React 19** (TypeScript frontend).

```mermaid
┌──────────────────────────────────────────────────────────┐
│                      MC-Vector App                        │
├──────────────────────────────────────────────────────────┤
│  Frontend (React + TypeScript)                            │
│  - UI Components  (src/renderer/components/)             │
│  - State          (Zustand stores in src/store/)         │
│  - IPC Wrappers   (src/lib/)                             │
│                          ▲                               │
│                          │  Tauri IPC (invoke / events)  │
│                          ▼                               │
│  Backend (Rust + Tauri v2)                               │
│  - Tauri Commands (src-tauri/src/commands/)              │
│  - Server process management (Tokio async)               │
│  - File system, HTTP, sysinfo                            │
│                          ▲                               │
│                          │                               │
│                          ▼                               │
│  External                                                │
│  - Minecraft server child processes                      │
│  - Plugin APIs  (Modrinth, Hangar, SpigotMC)            │
│  - Ngrok TCP tunnel                                      │
│  - Mojang API   (UUID resolution)                        │
└──────────────────────────────────────────────────────────┘
```

**Core data flow:** React components → `src/lib/` wrappers → `invoke()` → Rust commands → system resources

Security-sensitive commands enforce their policy in Rust. Filesystem operations resolve managed
roots from application-owned identifiers and relative paths; renderer-side allowlists are not a
security boundary. Provider downloads use typed source contracts, HTTPS and host allowlists,
bounded streaming, checksum verification, and atomic replacement. The global setting for plugin
artifacts without a published checksum is an explicit compatibility preference: it never disables
the remaining URL, path, archive, or resource-limit checks.

## Frontend

### Directory Structure

```
src/
├── renderer/components/     # Feature UI components
│   ├── DashboardView.tsx    # KPI tiles + real-time charts
│   ├── ConsoleView.tsx      # Log stream + command input
│   ├── FilesView.tsx        # File manager + Monaco editor
│   ├── PluginBrowser.tsx    # Plugin/mod search + install (state and IPC)
│   ├── plugin-browser/      # Plugin browser panels, cards, and dialogs
│   ├── BackupsView.tsx      # Backup create/restore
│   ├── UsersView.tsx        # Whitelist / ops / bans
│   └── ...
├── lib/                     # Tauri IPC wrappers
│   ├── server-commands.ts
│   ├── file-commands.ts
│   ├── plugin-commands.ts
│   ├── adapters/plugin/     # Legacy search signatures delegating to IPC
│   └── guards/              # Runtime type guards
└── store/                   # Zustand state stores
    ├── serverStore.ts
    ├── uiStore.ts
    ├── settingsStore.ts
    └── consoleStore.ts
```

### State Management (Zustand)

| Store              | Responsibility                                           |
| ------------------ | -------------------------------------------------------- |
| `useServerStore`   | Server list, selected server, status                     |
| `useUiStore`       | Current view, modal open/close, sidebar state            |
| `useSettingsStore` | Theme, language, update preferences                      |
| `useConsoleStore`  | Console log buffer (2,000 lines/server), command history |

**Persistent storage** is split by ownership:

- `server-registry.sqlite3` — Rust-owned server definitions and templates. On first launch, Rust imports existing records from `servers.json` and legacy template JSON when present; those JSON files remain read-only recovery sources.
- `config.json` — Ngrok token, app config
- `console-history` — per-server command history
- Other preferences continue to use the Tauri Store plugin (not localStorage).

Server status is runtime state: SQLite stores the server profile without its status field, and
`get_servers` derives `online` or `offline` from the Rust `ServerManager` map.

### IPC Wrapper Pattern

Components never call `invoke()` directly. All IPC goes through typed wrapper functions in `src/lib/`:

```typescript
// ✅ Correct — call a wrapper
import { startServer } from '../lib/server-commands';
await startServer(serverId);

// ❌ Incorrect — raw invoke
import { invoke } from '@tauri-apps/api/core';
await invoke('start_server', { serverId });
```

Plugin provider responses and installation decisions are fetched and parsed in Rust. The renderer receives UI DTOs through `plugin-commands.ts` and owns search presentation, filtering, translation, confirmation, and display formatting. Mojang and server-version integrations retain their current adapters.

## Backend

### Tauri Command Modules

```
src-tauri/src/commands/
├── server.rs          # Minecraft process supervision and runtime events
├── server_registry.rs # SQLite server profiles/templates and JSON migration
├── server_creation.rs # Validated, transactional server creation/import
├── server_lifecycle.rs# Clone/delete with registry and filesystem rollback
├── server_jar.rs      # Server JAR metadata, verified upgrade plans/downloads
├── plugin_catalog.rs  # Provider metadata command adapters
├── plugin_installer.rs# Preview/execute and plugin state command adapters
├── automation.rs      # Rust-owned restart and backup schedules
├── players.rs         # Whitelist, ops, ban list reads and mutations
├── properties.rs      # server.properties and proxy configuration
├── file_utils.rs      # Managed filesystem operations and safe imports
├── download.rs        # Bounded, verified artifact streaming and replacement
├── backup.rs          # ZIP backup / restore / compress / extract
├── java.rs            # Java JDK registry, download, extraction, and deletion
├── ngrok.rs           # Ngrok process, token, and download management
├── health_check.rs    # Minecraft Server List Ping (SLP)
├── process_stats.rs   # CPU + memory telemetry (sysinfo)
├── perf.rs            # ANSI log parsing (Rust-side for performance)
└── updater_utils.rs   # App self-update helpers
```

`commands/` contains the IPC boundary and feature services. Shared SQLite access,
operation locks, and OS-backed secret storage live under `src-tauri/src/state/`.
Blocking SQLite and filesystem work is dispatched with `spawn_blocking`; process,
network, and schedule work uses Tokio.

### Plugin Catalog Feature

`src-tauri/src/plugin_catalog/` owns Modrinth, Hangar, and Spiget metadata integrations. Provider
modules construct endpoints from fixed HTTPS API hosts and validated identifiers, parse provider
payloads, select compatible versions, and resolve artifact URLs and checksums. Search and detail
commands accept provider IDs, terms, and compatibility filters; renderer-supplied URLs and hashes
are not trusted. Metadata and download requests use bounded response streaming, timeouts, and
HTTPS host allowlists. React keeps search presentation, filters, translations, user confirmation,
and the installed-list display.

`src-tauri/src/plugin_installer/` owns the install transaction. A preview request resolves the
selected plugin and its dependencies in Rust and returns display data plus a short-lived, one-use
plan token. After the user confirms, execution downloads to managed staging paths, checks available
hashes (or consults the Rust-owned unverified-download policy), commits the full dependency set,
and records enough transaction state to roll back or recover interrupted file mutations. Enable,
disable, and uninstall operations also run in Rust. React passes the opaque plan token to execute;
it cannot change the planned URL, checksum, dependency graph, or target path after confirmation.
The explicit debug E2E build supplies deterministic local provider fixtures.

### Shared State (AppState)

Tauri-managed service state is shared across commands:

| State                  | Purpose                                                               |
| ---------------------- | --------------------------------------------------------------------- |
| `ServerRegistry`       | SQLite profiles/templates and legacy JSON migration                  |
| `ServerManager`        | Running child sessions, serialized commands, runtime status, metrics |
| `ServerOperationManager` | Per-server locks for conflicting file/process operations             |
| `PluginInstaller`      | Short-lived plans and recoverable plugin transactions                 |
| `AutomationManager`    | Restart policy and automatic backup schedule state                    |
| `NgrokManager`         | Active tunnel process and shutdown control                             |

### Event Bus

The backend emits Tauri events that the frontend listens to:

| Event                    | Payload                                                                                                   | Emitted by                         |
| ------------------------ | --------------------------------------------------------------------------------------------------------- | ---------------------------------- |
| `server-log`             | `{ serverId, generation, line, stream }`                                                                  | server.rs stdout/stderr            |
| `server-status-change`   | `{ serverId, generation, status, expected }`                                                               | server.rs on spawn/exit            |
| `server-stats`           | `{ serverId, cpu, memory, generation, sequence, elapsedMs }`                                              | server.rs, every 2 seconds         |
| `server-metrics-updated` | `{ serverId, generation, sequence, elapsedMs, resource, tps }`                                            | server.rs on each metric update    |
| `ngrok-status-change`    | `{ status, url }`                                                                                         | ngrok.rs                           |
| `download-progress`      | `{ downloaded, total }`                                                                                   | download.rs                        |
| `backup-progress`        | `{ serverId, progress }`                                                                                   | backup.rs                          |

### Process Management

1. `start_server` serializes operations per server, validates the server ID, Java runtime, memory args, and JAR path before spawning, then creates an in-memory metric session for that process generation.
2. Commands are sent through a bounded `mpsc` channel — never written directly to stdin from multiple callers.
3. stdout/stderr are buffered (4,096 lines) and forwarded to the frontend in batches (50 ms flush interval, max 200 lines/tick).
4. CPU and memory samples are kept for 60 seconds; Paper and LeafMC receive a `tps` query every 5 seconds, and matching stdout lines update the TPS history before log buffering.
5. `get_server_metric_history` returns the current session snapshot, while `server-metrics-updated` broadcasts the same shape with a monotonic generation and sequence.
6. Command input is rate-limited per server; process start/stop/restart and conflicting file operations share per-server operation locks.
7. Process sessions are removed only after the child is confirmed exited and reaped; metric history remains in memory only.
8. Rust publishes typed status transitions to its internal automation channel and emits the existing Tauri event for the UI. Renderer events cannot trigger automatic restart work.

## Key Data Flows

### Server Start

```
User clicks "Start"
→ DashboardView
→ startServer() (src/lib/server-commands.ts)
→ invoke('start_server')
→ Rust: validate → spawn Java process (Tokio)
→ Stream stdout → emit 'server-log' events
→ Emit 'server-status-change' (online)
→ Dashboard and Console update reactively
```

### Plugin Install

```
User clicks "Install"
→ PluginBrowser
→ Rust resolves provider metadata, compatibility, versions, and dependencies
→ Show install preview and ask the user to confirm
→ Rust issues a short-lived, one-use plan token
→ invoke('execute_plugin_install', { token })
→ Rust downloads and verifies artifacts in staging, then commits or rolls back the dependency transaction
→ Emit progress and completion state → UI updates
```

## Security Model

- **IPC allowlist** — only explicitly registered commands are callable from the frontend.
- **Path safety** — managed path resolvers reject traversal and links/reparse points; file mutations stay under application-managed roots and use staging/rollback where supported.
- **Input validation** — Rust commands validate IDs and request data, enforce per-server operation locks, and apply provider host, redirect, timeout, checksum, and size limits.
- **Credential handling** — the Ngrok token is stored through the OS credential store and redacted from process output; renderer-facing settings expose token status rather than the token value.
- **Persistence** — SQLite migration is transactional and keeps the legacy JSON source available for recovery. Server status is derived from active Rust process sessions rather than trusted from persisted or renderer-provided state.
- **No inline scripts** — CSP enforces `script-src 'self'`.
- **TLS everywhere** — all external HTTP requests use reqwest with certificate validation enabled.

## Technology Choices

| Technology   | Why                                                                           |
| ------------ | ----------------------------------------------------------------------------- |
| **Tauri v2** | Native performance, ~10–20 MB bundle vs Electron's ~100 MB, sandboxed WebView |
| **Rust**     | Memory safety, zero data races, Tokio async for concurrent process management |
| **React 19** | Concurrent rendering, modern hooks, Arc UI on top of Radix primitives, React Query |
| **Zustand**  | Minimal boilerplate, fine-grained subscriptions, no provider nesting          |
| **Bun 1.4.2** | Package management and workspace support for the root and `docs/` package       |
| **Oxlint**   | Fast linting for TypeScript, React, tests, and workspace scripts              |
| **Oxfmt**    | Consistent formatting for JavaScript, TypeScript, JSON, CSS, and Astro code   |
| **Lefthook** | Staged-file quality gates before commits                                      |
